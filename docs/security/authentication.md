# Authentication foundation

Browser authentication uses the opaque server-side session decision in ADR 0003. The database
stores a session-token hash; browser tokens must never be persisted in localStorage or logs.
Authentication resolves the current session, user, membership, organization and permissions on
the server. An arbitrary Authorization header does not establish an authenticated principal.

`createBrowserAuthentication` is the reusable route guard. Its session resolver accepts the
persisted session repository. Authentication precedes permission and organization ownership
checks. A protected route must use all applicable checks; CSRF is not authorization.

## Browser cookies and CSRF

The cookie helper uses HttpOnly, SameSite=Lax, Path=/ and no Domain. Production cookies also
require Secure and HTTPS. Plain HTTP cookies are permitted only in local development/test.
Revocation is authoritative in the database; logout must also clear the cookie with matching
attributes. Authentication mutations are not exposed in Phase 0.

For every unsafe cookie-authenticated request the guard requires both an exact trusted Origin
and `x-csrf-token`. The token is an HMAC with a dedicated server secret, bound to that browser's
session token and compared in constant time. A token from a different session fails. Rotating
the session invalidates the old CSRF token. A future authenticated CSRF-token response must be
non-cacheable and return the CSRF token only, never the session cookie value. GET, HEAD and
OPTIONS do not require a CSRF token and must never perform state changes.

The initial OTP/login flow will need trusted-Origin and request-content-type enforcement,
durable identifier/IP abuse limits, and its own pre-authentication CSRF decision before exposing
routes. The authenticated guard alone does not protect unauthenticated login mutations.

API-to-API credentials are not implemented. A future separate verified machine principal may
use its own authorization policy without browser CSRF requirements. An unverified Bearer
header never bypasses browser checks, including when cookies are also present.

## Secrets and logging

`CSRF_SECRET` and `OTP_HASH_SECRET` must each contain at least 32 bytes generated by a
cryptographically secure random generator. They are server-only environment values; production
requires distinct values. No hardcoded fallback exists. The OTP repository uses the latter
secret for challenge-bound digests. Development delivery is isolated from production and must
not log OTP codes. Production rejects development provider selections.

Operational logs omit request URLs, bodies, headers, raw exceptions and stack traces. Request
IDs are generated on the server. Error responses use safe problem details; malformed requests,
oversized bodies and rate limits retain their 400, 413 and 429 statuses. Future structured log
fields must be allowlisted; generic nested payloads must not be logged.

## Deployment and dependencies

The current general API rate limiter is process-local. A single API process is the verified
Phase 0 deployment boundary; multiple replicas require a shared limiter before exposure.
Durable OTP attempt/cooldown controls belong in PostgreSQL. Redis is optional because no
implemented session, cache, queue or worker adapter consumes it yet. Adding such an adapter
must add explicit configuration and readiness verification.

Production CORS origins require HTTPS. Blanket proxy trust is rejected in production; a future
deployment must explicitly configure trusted proxy addresses before using forwarded client IPs.
The running API checks PostgreSQL for readiness and disconnects its client on shutdown.
Payment webhook signature/replay contracts exist separately; no webhook endpoint is exposed.
